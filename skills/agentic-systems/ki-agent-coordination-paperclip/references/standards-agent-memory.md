# Agent memory and knowledge return

Agents may build familiarity without becoming the sole owners of company knowledge. Replacing an employee should lose familiarity, not the facts, decisions or learning needed to continue the company's work. Apply `ki-authoring`'s knowledge-promotion standard for placement and approval; this reference supplies the Paperclip memory and recurring-review boundary.

## Working memory, not a second knowledge base

- Keep company facts, decisions, commitments, procedures, work plans and delivery evidence in their owning repositories and declared durable stores. Company-wide knowledge normally belongs in the verified Agora home; repository-specific knowledge stays with its repository. Shared access does not mean public access.
- Agent-local memory may hold authorised retrieval hints, bounded run continuity and working techniques. Persistent personal preferences or patterns need the applicable opt-in and review; distinguish an observation from a confirmed preference. A memory skill assignment is not consent to enable auto-memory or override a repository's disabled-memory policy.
- Prefer a short retrieval hint with a canonical repository identity, locator and observed revision or date over copied business content. Re-read the source before relying on changing facts, authority or work state. A remembered approval is not a grant.
- Useful new knowledge may be captured provisionally with provenance and an explicit pending destination, using existing intake and approval rules. It must not quietly become a permanent private record. No agent may promote an unsupported inference into an established company fact.
- Keep memory, retrieval indexes and search access scoped to the authorised company and role. A shared laptop, principal or agent identity does not authorise cross-company reuse. Do not retain credentials, raw sensitive documents or unnecessary personal details in agent memory, shared reports or Git; use approved stores and non-secret locators.
- Reconcile a duplicate after its durable destination is verified: retain a minimal pointer or an explicitly justified cache. Do not erase the only evidence, bulk-delete memory or bypass applicable retention requirements. A reconciliation review is not deletion authority.

## Applying a bundled memory skill

When `para-memory-files` or an equivalent skill is available, managed agent instructions explicitly apply the boundary above. Its personal entity store and daily notes are working aids, not the authoritative company record. Its separate project-plan convention does not apply to KI work: planning enriches the governing work item through the selected adapter. Its retention advice does not authorise indefinite copying of sensitive material or prevent an authorised reconciliation with repository-owned knowledge.

Bootstrap and post-hire checks verify these instructions for every participating employee, not only the CEO. Preserve an intentional disabled-memory setting; do not enable memory, search indexing or new data collection just to run this check. Existing memory is reviewed within the approved scope, not silently migrated or deleted. Check the installed memory skill again after an upgrade for conflicting capture, planning or retention instructions.

## Weekly employee knowledge-return check

Make this a covered concern of the company's weekly work and knowledge reconciliation, preferably within its existing repository-review activity. It is an asynchronous employee contribution and repository reconciliation, not a new meeting or a task for every fact. Ad-hoc handovers, role changes and agent retirement use the same procedure. Normal delivery still returns important discoveries promptly.

The verified Agora home owns the shared definition and consolidated coverage report, unless an approved arrangement names another owner. Use its Project housekeeping definition or KB Activity according to repository kind; `ki-work-housekeeping` owns cadence, run reservation and successful-run evidence. Extend an equivalent review rather than creating a duplicate, preserving its identity, active run and prior evidence. Adopt weekly coverage explicitly with the employee scope, bounded review period, budget, evidence destination and applicable access; agree the actual day, time and timezone before activating a Paperclip routine. A pre-existing review schedule does not automatically authorise broader memory access.

### Procedure

1. **Ask each employee what should be shared.** Review their own authorised recent work, task outcomes and permitted working memory since that employee's last evidenced coverage, plus unresolved earlier candidates. A company review that missed an employee does not advance their coverage baseline. Do not mine unrelated conversations, another employee's private notes or other companies. Where no baseline exists, reuse an already-approved bounded initial window or agree one, rather than scanning all history. Do not wake paused employees without authority; record the coverage gap and owner.
2. **Return useful discoveries, not a memory dump.** For each candidate, state the learning or company fact, supporting evidence, uncertainty, proposed owning repository and whether a durable version already exists. A short “no new durable learning in this scope” return is valid; no contribution quota. Keep personal or restricted material out of the shared summary.
3. **Reconcile through the owning repository project.** Its authorised worker checks existing knowledge and open work, verifies sources and selects the narrowest durable home using `ki-authoring`. Update an existing record where appropriate. Coordination requests contributions and aggregates returned links only; it does not inspect or write repositories. Reuse an existing appropriately scoped task or review run rather than creating one per employee or observation.
4. **Promote within authority.** Save reviewed knowledge through the repository's normal writing, review and delivery rules. When additional approval is needed, keep one visible pending candidate in the existing intake or review record with an owner and next action. Proposed future work follows the selected work adapter; it is not silently adopted or implemented. Do not invent a separate company learning backlog or automatically convert raw memory into canonical notes.
5. **Verify the return and reconcile memory.** For delivered knowledge, verify its durable locator and revision before replacing an authorised duplicate with a pointer or recording why a cache remains useful. For an undelivered candidate, record its pending owner and next step while preserving the source evidence; a pending handoff is not permission to remove or reduce the only copy. Preserve access boundaries. A task comment alone does not prove repository delivery.
6. **Report coverage and gaps.** In the existing review result, identify employees and the period covered, useful knowledge returned with links, already-covered or rejected candidates, pending reviews and missing responses. Distinguish “review performed” from “all knowledge returned”; a missing response is not a no-findings result. Reuse unresolved candidates on the next run instead of raising duplicates.

### Completion and scheduling

Keep durable contributions in their owning repositories; the home report links them rather than reproducing each repository's knowledge. Successful-run evidence describes the actual coverage and any unresolved gaps under the adopted definition. Paperclip completion does not accept KI work, clear a reservation or advance successful-review evidence by itself. Reuse the same definition and active-run guard for weekly and ad-hoc calls. No memory reset, bulk export, cross-company indexing or schedule activation is implied by this standard.
