# Bootstrap or rebootstrap the current company

## What bootstrap does

- Find its repositories and give each one a clear project.
- Understand existing tasks, unfinished work, and anything on hold—without starting duplicates.
- Check whether current employees have clear responsibilities and can cover the work. Adjust their roles or assignments before suggesting hires.
- Set up useful regular checks and reports, based on what each repository needs.
- Make sure completed work can reach the user's local `main` checkout.
- Give a short list of what is working, what needs changing, and the few choices only the user can make.

## Regular checks to reconcile

- **Daily repository health:** check each repository's state with an audit and a preview of conform; do not make automatic repairs.
- **Daily company update at 08:00:** report yesterday's delivered results, today's focus, blockers and any incomplete health checks.
- **Regular next-work review:** ask each repository project to check its own roadmap or work queue, finish work already underway, and start approved Ready work when the required people, checks and delivery permission are in place. Otherwise bring back the smallest choice needed to unblock it. Do not start work merely because an item appears on the roadmap.
- **Weekly and on-demand repository review:** use the master checklist to look for drift, consolidation, learning, changed priorities and work that no longer makes sense.
- **Weekly work and knowledge reconciliation:** check held or unfinished work, task links, decisions, delivered evidence and useful learning. Combine this with the repository review where one run can cover both.
- **When relevant:** review team capacity and risk, check backup and recovery evidence with its owner, and recheck the arrangement after hires, membership, skill or runtime changes.

## Details for the agent

Read the canonical `ki-agent-coordination-paperclip` skill and its [existing-estate onboarding guide](../references/standards-existing-estate-onboarding.md). Infer the current company from the Paperclip run and verify its Agora binding from approved context and repository evidence; do not guess either from a name. Reuse existing projects, tasks, employees, definitions and routines. Reconcile repository projects, unfinished and held work, decisions, skill access, roadmap task links and recurring obligations without duplicating them. Repository inspection, planning and delivery belong in each owning repository project; Coordination only arranges and synthesises their returned evidence. Check clearer remits, reassignment and configuration before proposing hires.

The next-work check belongs to each repository project and uses that repository's selected `ki-work` adapter. Reconcile active, retained and awaiting-review or integration work before proposing new starts. Dispatch already approved Ready work only where the adapter supports execution and within its existing bounded authority, with the required implementer, independent reviewer, integration owner and workspace checks. A routine, a Paperclip assignment or a Ready label does not grant adoption, repository writes or integration. If authority, adapter support or a prerequisite is missing, return one short, contextual decision instead of silently starting work. Keep the repository's own recurring definition as the procedure and the Paperclip routine as its scheduling link; agree scope, timing, owner and safeguards before activation.

First return a read-only assessment and a one-screen, plain-language decision brief. Put detailed inventories, API evidence, exact diffs, history and future work in linked supporting records, not in the approval text. Ask approval for only the next bounded action: why it matters, who will do it, what it permits, what it does not permit, and what result will come back. Make each question understandable on its own: explain what happened, what has already been checked, why the person's answer is needed, the recommended choice and what happens if they wait. Do not seek repeat approval for unchanged accepted scope or another identical investigation when the real blocker is a missing owner or permission. Hold only the affected change while other authorised work continues. Do not create projects or tasks, move or hire agents, resume held work, change repositories, or activate schedules without the relevant approval. Daily preflight is audit plus conform dry-run only; follow the guide for the technical checks and evidence.
