# hooks

Knowledge Islands **agent runtime hooks**.

This directory is where the harness's hook scripts consolidate — the `PreToolUse`, `PostToolUse`, `Stop`, `SessionStart`, `PreCompact`, and similar handlers a consuming repo (or the personal `~/.claude/` environment) wires into a `settings.json`. The current surface has four concerns: the `plan-stamp.sh` / `plan-sync.sh` Plan Mode lifecycle pair, the `git-lock-check.sh` stale-lock guard, the `coordinator-reminder.sh` responsive-coordinator reminder and the `coordinator-footer.sh` footer check.

## How hooks are expected to work

A hook reaches a runtime in three parts, each with one owner, as Kris set on 6 November 2026: "I think that's the 3 aspects of how it works".

1. **Harness.** The harness ships each hook as `hooks/<hook>/<hook>.sh` and lists it in the [payload table](#payload) below, with its runtime, event, matcher and timeout.
2. **`ki`.** `ki` installs the payload to `~/.local/share/ki/harnesses/<org>/<harness>/hooks/`. For each registered harness, `ki doctor` reports each hook that is missing, unregistered in Claude Code or Codex, or lacking its current Codex trusted hash, and `ki repair` registers the missing ones. Where a dotfiles manager owns the settings, both report "managed by chezmoi, run chezmoi apply" instead of writing them.
3. **User-environment manager.** The user-environment manager, such as chezmoi, registers each hook from the installed path, never from a checkout.

Part 2 is the expected behaviour, not shipped behaviour. Its `ki` implementation is tracked with tools-ki through `ki.sop.main`'s tooling audit. Today `ki doctor` checks only that each harness is installed, and `ki repair` repairs only skill links and legacy configuration metadata; neither inspects or registers runtime hooks.

## Payload

`ki` installs every hook below with the harness, under `<installed harness>/hooks/`, which on a Mac is `~/.local/share/ki/harnesses/knowledgeislands/ki-agentic-harness/hooks/`. A user-environment manager registers each from that installed path, never from a source checkout; `payload.test.ts` keeps this table and the shipped executables in step.

Each hook has its own folder, `hooks/<hook>/`, holding its script `<hook>.sh` and its test `<hook>.test.ts`. The table gives each script's path under `hooks/`. `git-hooks/` holds no runtime hook: it carries the tests of the repository's own `.githooks/` `commit-msg` and `pre-commit` and of the stub a linked worktree runs in their place.

`plan-stamp.sh` records the authenticated current-session pointer at `~/.claude/plans/.state/<session_id>` as v1 JSON with exactly `version`, `session_id`, `plan_file`, and the hook event's physically resolved `cwd`. `plan-sync.sh` accepts only that validated JSON V1 state before updating progress; malformed, schema-invalid, and plaintext records fail closed. Neither hook promotes or writes a governed repository plan: promotion remains a deliberate `/ki-plan promote` action, and it preserves the scratch plan and state record.

`git-lock-check.sh` runs at `Stop(*)`. In the current Git worktree it removes stale `*.lock` files from the physical Git directory only when no relevant Git process is active. It exits successfully without mutation outside a worktree, when process state cannot be checked safely, or when a candidate no longer proves to be a real file beneath that Git directory. This guard recovers locks left by killed commands; it is not permission to interrupt write-mode Git operations.

`coordinator-reminder.sh` runs at `UserPromptSubmit` and `SessionStart` with the `compact` matcher. In a checkout declaring `[skills.ki-coordination]` it emits `hookSpecificOutput.additionalContext` with only a short conditional pointer: follow the coordination standard only when the owner explicitly opened or resumed coordination, otherwise use conversational Reply forms. Compact events point explicitly coordinating sessions to re-anchoring. The declaration and cwd establish checkout capability, never selected work or coordinator role; package, binding and session id alone do not establish those either. Unknown selection triggers no package enumeration, package reads or method Git-history scan. Full rules, reporting, re-anchoring and the per-coordinator method revision self-check stay in the authoritative standard and output style. Full session-sensitive detection remains deferred: the generic pointer is neither complete silence nor verified role detection. `ki-coordination` owns the generated `line` and `pointer` through its [generated surfaces](../skills/change-management/ki-coordination/references/standards-coordination.md#generated-surfaces); regenerate with `ki dev skill generate ki-coordination --write` rather than hand-edit them. The hook retains its subdirectory capability guard and early silence for `KI_AGENT_RUN` or the older Claude print-mode ceiling. Unsupported events, absent capability and malformed or unusable input fail open silently with success. Existing Claude Code and Codex payload fixtures exercise the shared event/output shape.

`coordinator-footer.sh` runs at `Stop(*)`. It reads a coordinating reply's footer against `ki-coordination`'s [Banner](../skills/change-management/ki-coordination/references/standards-coordination.md#banner) and [Summary](../skills/change-management/ki-coordination/references/standards-report-forms.md#the-summary) sections. It decides from the reply itself, which Claude Code passes as `last_assistant_message`, falling back to the transcript's last assistant entry. A reply needs a banner where it carries `## Summary` or a `Summary at` or `Status at` form line, a Bootstrap or Stop form line, a state heading or a thread line, and, with none of these, where the owner's last prompt was a mark, state word or Position phrase, such as `mark`, `mark, status only`, `status`, `summary`, `pause`, `snooze`, `with me`, `where are we` or `/ki-coordination drain`, in a checkout declaring `[skills.ki-coordination]`, and the session has already closed an earlier reply with a thread line, which is the cheapest reliable sign that it holds a work package; a plain answer, a run's wake and a conversational session stay quiet. A question outside the Position phrases, such as "what is waiting on me?", is not recognised. Where a banner is needed, the hook returns `decision: block` with a reason naming each missing part only for lost structure: no state heading, a `###` line opening with a glyph or naming a state, or no thread line, `<role glyph> 🔑 <work-id>` or `🧵 <work-id>`, as the last line. Every other unusual part passes with a non-blocking `systemMessage` warning naming it, so the owner can confirm it was intended: a state heading the table of states does not name, no counts line beneath the heading, none being needed under a Finished heading, a counts line opening with none of the counts glyphs, no listening line, `👂 listening` or `🔇 not listening`, under a named state other than Finished, and, in a Summary or Status, no art above the banner, unless the owner's last prompt asked for `no art`, no roadmap line, `🗺️ roadmap · none` standing where the checkout has no roadmap, or no package line. Any heading time form, `at` or `since`, and a form line written in an earlier layout, with its state, passes. Fenced text other than the art never counts. While `stop_hook_active` is set it never blocks twice, turning lost structure into a warning too. It is silent in launched agents and on a missing `jq`, unusable input or an unreadable transcript; it makes no network call, and reads at most the transcript's last 8 MiB, skipped to by `dd`. Codex's `Stop` event is unverified, so it is registered for Claude Code only.

The lock guard is best-effort recovery in a trusted user account. It rechecks candidate type, physical parent containment, and process state immediately before each removal, but portable shell cannot combine that parent proof and unlink into one descriptor-relative operation. It therefore does not claim to defend against a same-UID adversary concurrently replacing Git-administration path components.

Two ownership boundaries apply, and they deliberately diverge:

- **Repository-facing declarations** — a consuming skill may declare and audit that it needs a hook capability, but it does not write the user's global Claude settings.
- **Harness payload and runtime binding** — the verified compatible-harness payload installed by `ki` carries these hook sources. A user-environment manager owns any executable deployment and Claude Code registration derived from them. `ki bootstrap`, skill activation, and repository operations never write `.claude/settings.json` or mutate unrelated user hook state.

On a chezmoi-managed machine, `ki-repo-dotfiles-chezmoi` validates the selected payload and renders the matching Claude Code registrations. That binding is deliberately outside CLI harness installation and repository governance. Plan-file lifecycle is tied to personal `~/.claude/plans/` state; the lock guard applies across every worktree, so both remain home-directory capabilities rather than project-local hook installation.

The bundle layout remains governed by `ki-repo-harness`; `ki-plan` owns the Plan Mode lifecycle semantics; and `ki-git` owns the portable stale-lock guard contract. `ki-repo-dotfiles-chezmoi` retains runtime-specific Claude Code registration. No hook is an ungoverned policy surface.

The `plan-stamp.sh` / `plan-sync.sh` pair and Plan Mode discovery used by `/ki-plan promote` are bound to Claude Code's built-in interactive Plan Mode (the `EnterPlanMode`/`ExitPlanMode` tool pair). Per the runtime coverage in [SDR-KI-HARNESS-002](../docs/decisions/SDR-KI-HARNESS-002-runtime-portable-contracts-and-executor-positioning.md), that primitive has no known OpenAI Codex CLI equivalent, so this discovery bridge must not be assumed to port to a second runtime for free. The governed flat `docs/roadmap/<REPO>-<NNN>-<slug>.md` work-item artifact remains runtime-neutral. Codex CLI has its own hooks system with its own event set. `coordinator-reminder.sh` proves a shared executable is possible for `UserPromptSubmit` and `SessionStart`, whose input and `additionalContext` output Codex 0.162 implements in the Claude Code shape; Codex reads user hooks only from `~/.codex/hooks.json` and runs them only once `config.toml` trusts their hash. Every other event, and any plugin env-var convention, remains unverified, so further governed-hooks work must still establish cross-runtime portability event by event.
